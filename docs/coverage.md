# Coverage scorecard

Generated by `tools/coverage/run-corpus.sh` from the corpus in
`tools/coverage/corpus.tsv`; do not edit by hand. What a cell means is in
`tools/coverage/scorecard.py`, how a case is judged in
`tools/coverage/run-case.sh`.

Routes: **drop** is Enter on an unblessed image (whatever the loader does
by default), **chain** boots the ISO's own EFI loader, **bless** is Enter
on an image blessed with the sign tool.

BIOS is a fourth column and not a Secure Boot state: that machine has
no db and no shim, so it has no blessed cell and nothing to refuse.
BIOS, i686 is the same machine without a 64-bit mode, and is
where the 32-bit ISOs are judged; they are N/A under UEFI, whose loader
is x86-64, and the 64-bit ISOs are N/A there.
BIOS, i686 SSE2 runs the same ISOs on a processor with SSE2, PAE and
NX and still no 64-bit mode. BIOS, i686 is the Pentium III floor, with
neither SSE2 nor NX, so Windows 8 and later x86 failing there while
checking the processor is the expected result (`win_cpu_lacks`,
`falcon-bios/src/win/win.c`); BIOS, i686 SSE2 is where they are judged.

The headline columns are Secure Boot off and Secure Boot on where db
trusts the Microsoft CA. Secure Boot on with only the stick owner's
keys is reported beside them, without a target: media signed only by
Microsoft cannot boot on such a machine at all (DESIGN 7.2).
Secure Boot on with shim's validation off (MokSBState, DESIGN 7.4)
is run on request and reported without a target too: every ISO boots
there as with Secure Boot off, except a payload shim's own loader
cannot load (DESIGN 7.6, pfSense); a blessed Linux wrap is a UKI,
which does not boot in that state, so a refusal in its bless cell is
the expected result, while a blessed BSD medium or memtest86+ is its
own loader, signed, and boots. A chained loader still sees the
firmware's Secure Boot flag on, and one that enforces its own policy
from it fails as with validation on.

A cell reading "no userland on serial ... after starting <entry>" is a
measurement limit and not necessarily a failure. This harness reads
the serial console and a DHCP capture. A blessed wrap carries
console=ttyS0 because mk-case-stick.sh puts it there, and falcon-bios
appends it to a direct boot itself; a direct or chained boot under
UEFI runs the ISO's own cmdline, and an entry that writes to the
screen alone leaves both signals empty. Clonezilla is the worked
example (2026-09-20): its default entry is "Clonezilla live (VGA
800x600)", the screenshot beside the FAIL shows ocs-scan-disk running
and listing the disk it found, and serial stayed empty for 300s. Read
the screenshot before believing one of these.

A chain cell under UEFI for a Linux or BSD live ISO fails by design:
the ISO's own loader starts a system that cannot see the virtual CD
after ExitBootServices (DESIGN 6), and Enter's routes are the ones that
work. A Windows chain cell reaches Setup with no install source, since
c starts the installer unpatched. Scorecards before 1.0 counted many of
these as passing: the harness walked onto another row and Enter booted
the image (#26).

Known failures, each with its issue: memtest86-11-x64 on BIOS, since
the BIOS stick boots no .img (#13); windows-xp-pro-x64, which stops in
text-mode Setup with STOP 0x7B (#31). opnsense-25.1 is a harness limit:
a 4 GB q35 guest cannot hold its 2.2 GB image below 4 GB.

Loader: 1.0.0_20261113.1922.dev, 1.0.0_20261113.2257.dev, 1.0.0_20261113.2258.dev
